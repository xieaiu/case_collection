# 抖音直播弹幕获取程序改动说明

## 1. 文档范围

本次改动涉及以下文件：

- `获取弹幕.py`
- `mod.js`

以下文件未修改，但仍作为签名辅助文件保留：

- `获取sign.js`

原目录中没有名为 `danmu.py` 的文件，实际弹幕程序文件名为 `获取弹幕.py`。

## 2. 原程序问题

### 2.1 WebSocket 参数已经过期

原程序使用固定的 WebSocket URL 参数，其中包含固定的：

- `cursor`
- `internal_ext`
- `wss_push_room_id`
- `wss_push_did`
- `user_unique_id`
- `fetch_time`
- `seq`
- `signature`

这些参数属于页面运行时动态参数，不能长期硬编码。运行原程序时，WebSocket 握手返回了以下信息：

```text
Handshake status 200 OK
handshake-msg: DEVICE_BLOCKED
handshake-status: 415
```

这说明 WebSocket 没有成功建立可用的弹幕推送连接，因此 `on_message()` 没有机会收到弹幕数据。

### 2.2 收到消息后没有进行解码

原程序的消息回调只有以下逻辑：

```python
def on_message(ws, message):
    print(f"{ws}收到消息: {message}")
```

抖音直播消息不是普通文本，而是经过 Protobuf 编码的二进制数据。旧代码没有执行以下步骤：

- 解析 Protobuf 外层消息
- 识别 `WebcastChatMessage`
- 提取用户昵称
- 提取弹幕内容
- 保存弹幕原始 payload

### 2.3 页面信息获取不完整

原程序只提取了页面中的 `room_id`，没有动态提取当前页面对应的 `user_unique_id`。请求参数中的用户 ID 仍然是硬编码值，容易导致请求上下文与当前页面不一致。

### 2.4 签名脚本与 Node 22 运行时不兼容

`获取sign.js` 加载 `mod.js` 生成 `X-Bogus`。原 `mod.js` 在 Node.js 环境中执行时存在两个兼容性问题：

- 清空 Node.js 原生 `Buffer`，导致内部依赖调用 `Buffer.alloc()` 时失败
- 用浏览器模拟对象覆盖 Node.js 原生 `FinalizationRegistry`，导致 Node.js 内部 `undici` 模块初始化时报 `Illegal constructor`

需要区分 Node.js 版本：原程序在 Node 16 环境下可以运行。本次实际复现使用的是 Node 22，Node 22 的内置 Web API 和 `undici` 依赖初始化路径与 Node 16 不同，因此原 `mod.js` 中对 Node.js 全局对象的覆盖会触发兼容性错误。问题主要是运行时版本差异，不是 `获取sign.js` 中 `get_sign()` 的基本逻辑错误。

典型错误包括：

```text
TypeError: Cannot read properties of undefined (reading 'alloc')
```

```text
TypeError: Illegal constructor
```

## 3. `获取弹幕.py` 的改动

### 3.1 从 WebSocket 改为 HTTP 拉取接口

程序改用当前页面实际使用的接口：

```text
https://live.douyin.com/webcast/im/fetch/
```

该接口返回 Protobuf 格式的直播消息，当前验证可以正常返回包含聊天消息的二进制响应。

改动后的整体流程为：

```text
打开直播间页面
    -> 提取 room_id 和 user_unique_id
    -> 请求 /webcast/im/fetch/
    -> 解析 Protobuf Response
    -> 筛选 WebcastChatMessage
    -> 提取昵称和弹幕内容
    -> 更新 cursor 和 internal_ext
    -> 继续下一轮请求
```

### 3.2 动态提取直播间上下文

新增 `get_room_context()`，从直播间页面提取：

- `room_id`
- `user_unique_id`

函数会检查页面请求状态。如果页面中找不到必要字段，会抛出明确错误，而不是继续使用错误的固定参数。

### 3.3 新增 Protobuf 基础解析器

新增以下函数：

- `read_varint()`：读取 Protobuf Varint
- `iter_fields()`：遍历 Protobuf 字段
- `decode_text()`：将字节字段转换为 UTF-8 文本

解析器目前支持常见的 Protobuf wire type：

- `0`：Varint
- `1`：固定长度 64 位字段
- `2`：长度限定的字节字段
- `5`：固定长度 32 位字段

### 3.4 新增聊天消息解析

新增 `parse_chat_message()`，按照抖音直播聊天消息结构提取：

```python
{
    "nickname": "用户昵称",
    "content": "弹幕内容",
    "raw_payload": b"..."
}
```

字段映射如下：

- 聊天消息的字段 `2`：用户对象
- 聊天消息的字段 `3`：弹幕文本
- 用户对象的字段 `3`：用户昵称

其中 `raw_payload` 保存的是当前 `WebcastChatMessage` 的原始 Protobuf payload，类型为 `bytes`。该字段目前保存在内存对象中，默认不会写入文件。

### 3.5 新增 Response 解码

新增 `parse_response()`，完成以下工作：

- 遍历 Response 中的消息列表
- 提取消息方法名
- 提取消息 payload
- 仅处理 `WebcastChatMessage`
- 提取服务器返回的 `cursor`
- 提取服务器返回的 `internal_ext`

### 3.6 支持游标续拉

每次请求成功后，程序会使用服务端返回的游标更新下一次请求参数：

```python
params["cursor"] = cursor
params["internal_ext"] = internal_ext
```

这样可以避免每次请求都从固定位置开始，降低重复消息和失去消息位置的概率。

### 3.7 增加异常处理和重试

新增以下防护：

- HTTP 请求异常后等待 1 秒重试
- 空响应自动等待后重试
- 检查响应是否为 Protobuf
- Protobuf 解码失败时抛出明确错误
- 直播接口返回非 Protobuf 内容时输出响应类型和响应片段

### 3.8 支持命令行传入直播间地址

默认直播间地址为：

```text
https://live.douyin.com/6096197105
```

也可以传入其他直播间地址：

```powershell
python .\获取弹幕.py https://live.douyin.com/直播间ID
```

## 4. `mod.js` 的改动

### 4.1 保留 Node.js 原生 `FinalizationRegistry`

在浏览器模拟环境定义 `FinalizationRegistry` 前，先保存 Node.js 原生实现：

```javascript
var v_native_FinalizationRegistry =
    typeof FinalizationRegistry != 'undefined'
        ? FinalizationRegistry
        : undefined

FinalizationRegistry = v_native_FinalizationRegistry || 浏览器模拟实现
```

这样可以避免 `mod.js` 覆盖 Node.js 内部依赖需要的原生构造函数。

### 4.2 Node.js 环境保留原生 `Buffer`

原逻辑无条件清空 `Buffer`。现在只有在没有 `process` 的浏览器模拟环境中才清空：

```javascript
if (typeof Buffer != 'undefined' && typeof process == 'undefined') {
    Buffer = undefined
}
```

在 Node.js 中，原生 `Buffer` 会继续保留，使 CryptoJS 和 Node.js 内部模块能够正常工作。

## 5. `获取sign.js` 的现状

`获取sign.js` 本次没有改动，仍然通过以下方式生成签名：

```javascript
function get_sign(room_id) {
    // 根据 room_id 生成 MD5
    // 调用 window.loader 生成 X-Bogus
}
```

由于 `mod.js` 已增加 Node 22 兼容处理，`获取sign.js` 可以在当前 Node 22 环境中通过 ExecJS 正常执行，并返回 `X-Bogus`。在原来的 Node 16 环境中不需要这项兼容处理也可以运行。

需要注意：当前修复后的 `获取弹幕.py` 使用 `/webcast/im/fetch/` 接口拉取弹幕，没有再依赖本地 `X-Bogus` 生成流程。`获取sign.js` 作为其他接口请求的辅助脚本保留。

## 9. 当前限制

### 9.1 原始 payload 尚未落盘

`raw_payload` 目前只保存在解析结果字典中。如果需要保存原始弹幕数据，需要在 `fetch_danmu()` 中增加文件写入或数据库存储逻辑。

建议保存为二进制文件或 Base64，不建议直接把 Protobuf bytes 当作文本写入。

### 9.2 使用 HTTP 轮询而不是长连接

当前实现使用 HTTP 接口循环请求，优点是参数获取简单、稳定性较好；缺点是相比 WebSocket 可能存在轻微延迟。

### 9.3 Protobuf 字段解析范围有限

当前程序重点解析聊天消息所需字段，没有完整实现所有抖音直播消息类型。如果后续需要礼物、点赞、入场、关注等消息，需要根据对应消息类型继续增加字段解析。

### 9.4 页面结构变化风险

`room_id` 和 `user_unique_id` 当前从直播间页面内嵌数据提取。如果抖音修改页面数据结构或字段转义方式，需要同步调整正则表达式。

### 9.5 接口及风控参数可能变化

抖音接口参数、请求频率和风控策略可能变化。出现非 Protobuf 响应、空响应、状态码异常或请求被限制时，应优先重新检查浏览器中的实际请求参数，而不是继续复用旧的固定参数。
